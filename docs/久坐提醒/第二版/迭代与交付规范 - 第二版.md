# 迭代与交付规范-第二版

## 1. 迭代计划

### 1.1 版本迭代目标

交付久坐提醒第二版：**免打扰多时段 + 推迟调度 + v2 本地持久化**；后端命令保持兼容。

### 1.2 迭代里程碑节点

| 里程碑 | 说明 |
|--------|------|
| M1 设计冻结 | 七份第二版文档归档 |
| M2 开发完成 | 前端实现与自测通过 |
| M3 回归完成 | 第一版核心用例与第二版增量用例通过 |
| M4 发布候选 | 打包 RC |

### 1.3 任务拆分与排期

前端主导；后端仅需验证无签名变动下的冒烟；测试编写用例表。

## 2. 代码管理规范

### 2.1 分支管理规则

建议使用分支名：`久坐提醒-第二版`；合并前发起 Pull Request。

### 2.2 代码提交规范

提交信息包含：`久坐提醒-第二版`、变更点关键词、关联设计章节（如「附录 B 推迟算法」）。

### 2.3 代码合并与评审规则

至少一名评审；调度算法变更必须附加测试说明或手工验证记录。

## 3. 构建与打包规范

### 3.1 构建环境要求

与第一版锁定版本一致。

### 3.2 构建流程规则

版本号升级：`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 与 `get_app_info`（`src-tauri/src/commands/app.rs` 中返回的 `version` 字段）**四者一致**，作为第二版交付检查项（修复历史不一致）。

### 3.3 打包产物规范

Windows 安装包资产随 Release 流程上传；Release Note 明确「免打扰时段」与迁移说明。

### 3.4 补丁/插件交付适配规则

免打扰属于核心前端能力，**不建议**以插件形式交付；若未来补丁化需单独评审。

## 4. 发布与部署规范

### 4.1 发布流程

标签驱动 CI → Draft Release → 验证迁移说明 → Publish。

### 4.2 部署环境要求

与第一版一致。

### 4.3 灰度发布规则

可先面向内测标签用户收集迁移反馈。

## 5. 回滚规范

### 5.1 回滚触发条件

第二版出现大规模调度错误或配置迁移事故。

### 5.2 回滚执行步骤

1. 代码回退至第一版标签构建。
2. 用户侧若已写入 v2：**不建议自动删除**；需在支持文档说明手动清理策略或提供「重置配置」入口（未来改进项）。

### 5.3 回滚验证标准

第一版核心用例全通过；用户可在清空浏览器本地数据后恢复初始状态（明示风险）。

## 6. 交付物清单

### 6.1 设计文档清单

第二版全部七份文档 + 第一版七份文档（历史基准）。

### 6.2 代码产物清单

变更后的前端源码与类型声明；若版本号修复涉及 `app.rs` 则包含对应改动。

### 6.3 验收交付物清单

测试记录（含迁移与链式跳过）、Release Note、已知问题列表。

## 7. 验收标准

### 7.1 功能验收标准

满足《需求规格说明书-第二版》量化验收条目。

### 7.2 质量验收标准

P0 缺陷清零；构建零错误；类型检查零误差。

### 7.3 交付验收流程

测试出具报告 → 产品确认 → 架构确认文档与实现一致性。

## 8. 线上运维规范

### 8.1 线上问题处理流程

区分「调度错误」与「迁移错误」标签；优先收集本地配置样例（脱敏）。

### 8.2 日志与监控规范

前端可在超限兜底时打点本地日志（可选）；不上传远端。

### 8.3 迭代优化规则

跨午夜与按周规则进入第三版候选需求池。
